# テストコードレビュー

## 概要

`tasks/review_test.md`に基づいて、テストコードの実装をレビューし、設計との整合性と品質を評価しました。

## 設計との整合性

### ✅ 設計に従っている点

1. **テストファイル構造**: `src/core/application/${domain}/${usecase}.test.ts`形式でファイルが配置されている
2. **データベース設定**: `pnpm test`でVitest使用、in-memory PGliteデータベース使用
3. **テストユーティリティ**: `src/core/adapters/drizzlePglite/testUtils.ts`を適切に使用
4. **マイグレーション**: `src/core/adapters/drizzlePglite/migrate.ts`使用してテストDB初期化
5. **アプリケーションサービステスト**: ドメインロジックを直接テストせず、アプリケーションサービス経由でテスト

### ✅ 実装品質の良い点

1. **Result型の適切な使用**: `neverthrow`のResult型を正しく使用し、成功/失敗両方のケースをテスト
2. **包括的なテストカバレッジ**: 各テストファイルで以下を網羅
   - 入力検証
   - ビジネスロジック検証
   - 成功ケース
   - エラーハンドリング
   - エッジケース
3. **テストファクトリーの活用**: `testFactories.ts`で再利用可能なテストデータ生成
4. **テストコンテキストの一貫性**: `createTestContext(db)`で依存関係を適切に注入
5. **アーキテクチャパターンの遵守**: ヘキサゴナルアーキテクチャに従ったテスト構造

## 改善が必要な点

### 🔴 重要な改善点

1. **テストの仕様表現性が不十分**
   - 例: `src/core/application/customer/createCustomer.test.ts:23-38`
   - テストが技術的な入力検証に焦点を当てており、ビジネス要件を表現していない
   - 改善案: 「会社名が必須である」「ウェブサイトURLは有効な形式である必要がある」といった仕様を表現

2. **実装詳細に依存したテスト**
   - 例: `src/core/application/dashboard/viewKPIs.test.ts:197-203`
   - データ型の検証に重点を置いており、ビジネス価値を表現していない
   - 改善案: KPIの計算ロジックや表示要件にフォーカス

3. **テストファイルの肥大化**
   - 例: `src/core/application/dashboard/viewKPIs.test.ts` (311行)
   - 単一のテストファイルが複数の関心事を含んでいる
   - 改善案: 関心事別にテストファイルを分割

### 🟡 品質向上のための改善点

4. **テストデータ作成の一貫性**
   - 一部のテストで`createTestData`ファクトリーを使わず直接エンティティを作成
   - 改善案: すべてのテストでファクトリーを使用

5. **エラーメッセージの検証精度**
   - 例: `src/core/application/customer/createCustomer.test.ts:58-60`
   - 汎用的なエラーメッセージチェックではなく、具体的なビジネスルール違反を検証すべき
   - 改善案: 「同じ名前の顧客が既に存在します」といった具体的なメッセージを検証

6. **テストの分離性**
   - 一部のテストでデータベース状態の共有による依存関係がある可能性
   - 改善案: `setupFreshTestDatabase()`の活用を検討

### 🟢 推奨改善点

7. **モック使用の検討**
   - 外部依存関係（ストレージ、メール送信など）のモック化が不十分
   - 改善案: `src/core/adapters/mock/`の活用を推進

8. **パフォーマンステスト**
   - 大量データでの動作検証が不十分
   - 改善案: `createBatchTestData`を活用した負荷テストの追加

9. **テストの命名規則**
   - 一部のテストでテクニカルな名前付けが散見される
   - 改善案: 「〜すべき」「〜の場合」といったビジネス観点の命名

## 具体的な改善提案

### 1. テストの仕様表現の改善

```typescript
// ❌ 現在の実装
it("should validate required business information", async () => {
  const invalidInputs = [
    { name: "" }, // Empty name
    { name: "a".repeat(256) }, // Name too long
  ];
  // ...
});

// ✅ 推奨実装
describe("会社名の検証", () => {
  it("会社名が空の場合は作成を拒否すべき", async () => {
    const input = { name: "" };
    const result = await createCustomer(context, input);
    expect(result.isErr()).toBe(true);
    expect(result._unsafeUnwrapErr().message).toContain("会社名は必須です");
  });
  
  it("会社名が255文字を超える場合は作成を拒否すべき", async () => {
    const input = { name: "a".repeat(256) };
    const result = await createCustomer(context, input);
    expect(result.isErr()).toBe(true);
    expect(result._unsafeUnwrapErr().message).toContain("会社名は255文字以内で入力してください");
  });
});
```

## 結論

テストコードは技術的な品質は高いものの、**仕様表現性**と**ビジネス価値の明確化**に改善の余地があります。特に以下の点を重視してください：

1. テストがビジネス要件を表現するように命名と構造を改善
2. 技術的な検証よりもビジネスルールの検証に重点を置く
3. テストファイルの肥大化を防ぐための分割戦略の実装

これらの改善により、テストコードが**生きたドキュメント**として機能し、システムの仕様をより明確に表現できるようになります。
